# Step 03: 실행 모드 선택

## MANDATORY RULES (반드시 먼저 읽기):

- 📖 이 파일을 끝까지 읽은 뒤에만 행동한다
- 🎯 세 가지 모드의 차이를 명확하게 설명하고 사용자가 고른다
- 💡 기본 권장은 "혼합(Mixed)" — 단, 강요하지 않는다
- 🔒 모드 선택은 `.decision-log.md`에 기록한다
- 💬 `{communication_language}`로 모든 출력을 작성한다

## 이 단계의 목표

에이전트가 계약서를 얼마나 엄격하게 따를지 결정한다. 모드에 따라 생성되는 파일의 상세도가 달라진다.

---

## 실행 순서

### A. 모드 설명 제시

```
📐 실행 모드를 선택해 주세요.

모드는 계약서가 에이전트에게 얼마나 많은 것을 지시할지 결정합니다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[T] 타이트 (Tight) — 에이전트 자율 최소화
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• API: 모든 필드명, 타입, 필수 여부, 에러 코드 명시
• WS: 페이로드 스키마, 순서, 재시도 정책 명시
• DB: 컬럼 타입, 인덱스, 제약조건, 마이그레이션 순서 명시
• 어댑터: 메서드 시그니처, 예외 타입, 타임아웃값 명시

적합한 경우: 여러 팀이 병렬 개발 / 외부 API 공개 / 규정 준수 필요

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[R] 러프 (Rough) — 에이전트 자율 최대화
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• API: 목적과 HTTP 메서드만 명시 (필드는 에이전트가 판단)
• WS: 이벤트명과 방향만 명시
• DB: 엔티티명과 핵심 관계만 명시
• 어댑터: 외부 시스템명과 기능 목적만 명시

적합한 경우: 단일 팀 개발 / 초기 탐색 단계 / 에이전트 유연성 우선

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[M] 혼합 (Mixed) ★ 권장
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• 핵심 연결 지점(인터페이스 경계)은 타이트하게 명시
• 내부 구현 세부사항은 에이전트 자율에 맡김
• 각 인터페이스 포인트마다 "타이트 / 러프" 레이블 부여

권장 이유: 팀 간 계약은 명확히, 단일 에이전트 내부는 유연하게

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

선택하세요: [T] 타이트 / [R] 러프 / [M] 혼합
```

### B. 혼합 모드 선택 시 — 항목별 레이블 안내

사용자가 [M]을 선택하면 추가 안내를 제공한다:

```
📐 혼합 모드를 선택하셨습니다.

다음 단계(설계 결정)에서 각 인터페이스 포인트마다
타이트/러프 레이블을 함께 결정하게 됩니다.

기본 원칙 (변경 가능):
- 타이트 기본: 외부 어댑터, 외부 공개 API
- 러프 기본: 내부 WebSocket 이벤트, 내부 DB 테이블

[C] 계속
```

### C. 결정 기록

모드 선택을 `.decision-log.md`에 기록한다:

```markdown
| {n} | {date} | 실행 모드 | {T/R/M} — {모드명} | {사용자가 밝힌 이유 또는 기본 이유} | {user_name} | 확정 |
```

---

## SUCCESS CRITERIA:

✅ 세 가지 모드를 명확하게 설명  
✅ 사용자가 직접 선택  
✅ 선택을 `.decision-log.md`에 기록  
✅ 혼합 모드 선택 시 항목별 레이블 안내  

## FAILURE MODES:

❌ 사용자 확인 없이 기본 모드 자동 적용  
❌ 모드 선택을 결정 로그에 미기록  
❌ 혼합 모드의 항목별 레이블 안내 생략  

## NEXT STEP:

사용자가 모드를 확정하면 `./step-04-decisions.md`를 로드하여 설계 결정 협업을 시작한다.
