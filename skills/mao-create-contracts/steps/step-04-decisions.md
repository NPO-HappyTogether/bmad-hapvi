# Step 04: 설계 결정 협업 (핵심)

## MANDATORY RULES (반드시 먼저 읽기):

- 📖 이 파일을 끝까지 읽은 뒤에만 행동한다
- 🛑 결정이 필요한 포인트마다 사용자가 직접 선택하도록 한다
- 📋 에이전트가 결정을 내리지 않는다 — 옵션을 제시하고 근거를 설명한다
- 📝 모든 결정을 즉시 `.decision-log.md`에 기록한다
- 🔬 "깊게 봐줘" 요청 시 세 관점 멀티에이전트 분석을 제공한다
- ⚡ PRD에서 명확히 확정된 사항은 결정 포인트로 제시하지 않는다
- 💬 `{communication_language}`로 모든 출력을 작성한다

## 이 단계의 목표

Step 02에서 추출한 인터페이스 포인트 중 **설계 선택이 필요한 지점**마다 옵션을 제시하고, 사용자 결정을 이끌어내어 계약서의 기초를 확정한다.

---

## 결정 포인트 탐지 기준

아래 신호가 있는 인터페이스 포인트는 결정 포인트다:
- 구현 방식이 여러 가지일 때 (예: REST vs GraphQL, UUID vs ULID)
- PRD에 "추후 결정", "TBD", "논의 필요" 표시가 있을 때
- 에러 처리 전략이 명시되지 않았을 때
- 인증/인가 범위가 불분명할 때
- 외부 시스템 연동 계약 방식이 열려 있을 때

---

## 결정 포인트 진행 형식

각 결정 포인트마다 아래 형식으로 제시한다:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📐 결정 포인트 #{n} — {포인트 이름}
관련: {인터페이스 포인트 ID, 예: A-003, W-001}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

{이 결정이 왜 필요한지 한 문장}

┌─ 옵션 A: {이름}
│  {설명} (1~2줄)
│  장점: {핵심 장점}
│  단점: {핵심 단점}
│
├─ 옵션 B: {이름}
│  {설명} (1~2줄)
│  장점: {핵심 장점}
│  단점: {핵심 단점}
│
└─ 옵션 C: {이름} (있는 경우)
   {설명} (1~2줄)

선택하세요:
[A] {옵션 A 이름}
[B] {옵션 B 이름}
[C] {옵션 C 이름} (있는 경우)
[D] 깊게 봐줘 — 세 관점 멀티에이전트 분석 요청
[S] 건너뛰기 — 에이전트 자율에 맡김 (러프 처리)
```

---

## 멀티에이전트 분석 프로토콜 ([D] 선택 시)

사용자가 [D]를 선택하면 세 관점에서 분석을 제공한다.

**서브에이전트 가용 시 (권장):**
세 페르소나를 병렬 서브에이전트로 실행한다.

각 서브에이전트 프롬프트:
```
당신은 {페르소나 이름} ({역할})입니다.

## 분석 대상
결정 포인트: {포인트 이름}
옵션들: {옵션 A/B/C 전문}
프로젝트 컨텍스트: {관련 PRD 발췌}

## 당신의 관점
{focus 설명}

## 지침
- {페르소나 이름}의 목소리와 전문성으로 응답하세요
- {icon} **{이름}:** 으로 시작하세요
- {communication_language}로 응답하세요
- 각 옵션에 대한 명확한 입장을 밝히세요
- 다른 에이전트와 의견이 다르면 솔직하게 말하세요
- 도구를 사용하지 마세요. 관점만 제시하세요
```

**서브에이전트 불가 시 (--solo 모드):**
세 페르소나를 직접 롤플레이하여 순차적으로 응답한다. solo 모드임을 사용자에게 먼저 알린다.

**분석 결과 제시 형식:**
```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔬 멀티에이전트 분석 — {결정 포인트 이름}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🏗️ **Winston (기술 아키텍트):**
{Winston의 분석}

⚙️ **Amelia (구현 엔지니어):**
{Amelia의 분석}

🧪 **Murat (QA 아키텍트):**
{Murat의 분석}

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

분석을 검토하셨나요? 이제 결정을 내려주세요:

[A] {옵션 A} / [B] {옵션 B} / [C] {옵션 C}
[S] 건너뛰기 — 에이전트 자율
```

---

## 결정 즉시 기록

사용자가 선택하면 즉시 `.decision-log.md`에 추가한다:

```markdown
| {n} | {date} | {결정 포인트 이름} | {선택한 옵션 및 내용} | {근거 — 사용자 발언 또는 분석 결과} | {user_name} | 확정 |
```

[S] 건너뛰기 선택 시:
```markdown
| {n} | {date} | {결정 포인트 이름} | 에이전트 자율 (러프) | 사용자가 에이전트 판단에 위임 | {user_name} | 위임 |
```

## 결정 포인트 예시 목록

(PRD 분석 후 실제 포인트를 생성한다. 아래는 일반적인 예시다.)

**API 범주에서 빈번한 결정 포인트:**
- `DP-01` — ID 체계: UUID v4 / ULID / 자동증가 정수
- `DP-02` — 페이지네이션: 커서 기반 / 오프셋 기반
- `DP-03` — 에러 응답 형식: RFC 7807 Problem Details / 자체 포맷
- `DP-04` — 인증 토큰 전달: Authorization 헤더 / 쿠키 / 쿼리파라미터

**WebSocket 범주:**
- `DP-05` — 재연결 전략: 지수 백오프 / 고정 간격 / 사용자 이벤트 트리거
- `DP-06` — 이벤트 직렬화: JSON / MessagePack / Protocol Buffers

**DB 범주:**
- `DP-07` — 소프트 삭제: deleted_at 컬럼 / 별도 archive 테이블 / 즉시 삭제
- `DP-08` — 낙관적 잠금: version 컬럼 / ETag / CRDT 의존

**외부 어댑터 범주:**
- `DP-09` — 어댑터 실패 처리: 서킷 브레이커 / 재시도 큐 / 즉각 실패
- `DP-10` — 어댑터 인터페이스 계약: 추상 클래스 / 인터페이스 / 덕 타이핑

## 전체 결정 완료 시

모든 결정 포인트를 처리하면:

```
📐 모든 설계 결정이 완료되었습니다.

**확정된 결정:** {n}개
**에이전트 자율 위임:** {m}개
**총 인터페이스 포인트:** {k}개

결정 로그: _bmad-output/contracts/.decision-log.md

[C] 계속 — 00-index.md 생성
```

---

## SUCCESS CRITERIA:

✅ 결정 포인트마다 옵션 A/B(/C) 제시  
✅ [D] 요청 시 세 관점 분석 제공  
✅ 모든 결정을 즉시 `.decision-log.md`에 기록  
✅ PRD 확정 사항은 결정 포인트로 재제시하지 않음  
✅ [S] 건너뛰기도 결정 로그에 "위임"으로 기록  

## FAILURE MODES:

❌ 에이전트가 사용자 대신 결정  
❌ 결정 직후 기록 지연  
❌ [D] 요청 시 멀티에이전트 분석 생략  
❌ PRD에 이미 명시된 사항을 결정 포인트로 재제시  
❌ 결정 포인트 건너뜀 (중요 포인트 누락)
